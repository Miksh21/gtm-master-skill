### Competitor monitoring
- Every competitor signal carries article date AND event date; only event date counts for freshness (syndicated/recap pieces put fresh dates on old events). Resolve event date from the body: explicit past reference > relative time resolved against article date > present-tense "today announces" > dateline; date-filtered search filters by publish date and never establishes truth. [alon-goldenberg/competitor-monitoring]
- Source hierarchy PRIMARY (own domain, press release, filing) > WIRE > MAJOR bylined > DERIVATIVE. P1 moves (M&A, C-suite/VP move, funding >$10M, directly competing launch) with only a derivative source or low date confidence must be matched to a primary source: inside window = NEW, outside = STALE (drop), no primary = UNCERTAIN (drop). Verification spend scales with priority (P1 always extract+corroborate, P3 never). [alon-goldenberg/competitor-monitoring]
- Four freshness classes NEW / UPDATED / STALE / UNCERTAIN; only NEW and UPDATED enter the report or memory, since stale entries in memory poison every future dedup (stricter than detect-signals-from-list.md:62: STALE is banned even as background, except a labelled 1-3 line "Older context"). Return signals as fixed records (SIGNAL, ARTICLE_DATE, EVENT_DATE, URL, SOURCE_TYPE, DATE_CONFIDENCE, NEEDS_CORROBORATION, TYPE, PRIORITY); merge same event on company+type+approx date, keep the best URL, count distinct sources as confidence. [alon-goldenberg/competitor-monitoring]
- Per competitor, 5 parallel queries: news; "funding OR acquisition OR hiring"; changelog/release notes restricted to their domain (cheapest primary-source signal, already dated); x.com/linkedin.com past week (social lands days before press); G2/Capterra. Concrete dates in query text, ~8 actions per competitor per run, deeper = follow-up. [alon-goldenberg/competitor-monitoring]
- Run mode keyed to last run: >14 days = full 14-day window; <14 days = refresh since last run with a 7-day floor (near-empty windows read as false quiet); same-day repeat = ask first. Name quiet competitors explicitly and add a cross-competitor section for moves converging across 2+ rivals. [alon-goldenberg/competitor-monitoring]
- Per-field provenance: every dossier field is {value, source_url, fetched_at, status}; unfindable = null + not_found, blocked page = blocked; model knowledge is never a source. [sabahudin-murtic/competitive-intelligence-radar]
- Week-over-week diffs only across fields fresh on BOTH sides (pricing and SERP re-fetched every run; news, sentiment, hiring valid 30 days; funding 90 days); rank changes by materiality and lead with a three-item focus list. [sabahudin-murtic/competitive-intelligence-radar]
- Gather with isolated per-competitor scouts (capped at 8, no cross-talk); analyse in a debating panel that includes a devil's advocate, and cut or downgrade any recommended move that does not survive the challenge. Hiring is read as a leading indicator of product direction. [sabahudin-murtic/competitive-intelligence-radar]

### Inbound and relationship signals
- LinkedIn DM triage as a priority-ordered, first-match-wins taxonomy: vendor spam (skip) > customer support (urgent) > customer commercial (expansion, renewal, churn risk) > active pipeline > re-engagement (only with prior sales-touch evidence) > high-ACV prospect > low-ACV prospect > partner > speaking > VC > collaboration > unknown (to a human, never force-classified). [ariel-cohen/linkedin-dm-signal-classifier]
- Poller cursor is written only at the END of a fully successful run, using the run START timestamp: duplicate processing on retry is acceptable, silently skipped signals are not. Post a digest even on zero-signal days, so silence always means failure, never "nothing found". [ariel-cohen/linkedin-dm-signal-classifier]
- 7-day per-contact dedup: re-alert only when a new inbound message adds materially new information (new ask, timeline, objection, intent shift), as a short update, not a full post. [ariel-cohen/linkedin-dm-signal-classifier]
- (single-case: one vendor's tiers and self-serve gate) A substantive inbound DM lifts an account at most one tier when it sits just below the alert tier, and a run never lowers a tier; the self-serve gate (<50 employees AND <=$10M funding, using the lower headcount of enrichment vs LinkedIn) fires before scoring even on a strong DM. [ariel-cohen/linkedin-dm-signal-classifier]
- The person already in the DM thread is never enrolled in a sequence (they get a drafted reply in the owner's voice); other committee members may be sequenced, always approval-queued, because a human relationship is in motion. [ariel-cohen/linkedin-dm-signal-classifier]
- Job-change company sameness by hard identifiers: normalized registrable domain (handles co.uk) > LinkedIn /company/ slug > name only as support after stripping legal suffixes, never enough for a CRM write. Verdicts Match / Ambiguous (no write) / Different (disagreeing domains beat name similarity); rebrands and acquisitions count as same only when domain or LinkedIn page agree. [jorge-macias/track-contact-job-changes]
- Validate the enriched profile's name against the CRM contact at both URL-finding and work-history steps; a mismatch means the stored URL is likely wrong, so "can't confirm", never a write. [jorge-macias/track-contact-job-changes]
- Propose-then-confirm: collect all job-change writes in one review table (contact, old -> new company, outcome, evidence) and apply only approved rows; keep the old company as previous-role history. [jorge-macias/track-contact-job-changes]
- New-employer tiering scores only the criteria the operator defined (blank = not a filter); all pass = propose account creation; any fail = skip but still update the contact's company and title so the record is honest; nothing scorable = non-fit by default. [jorge-macias/track-contact-job-changes]
- Groundswell play as a ladder: gather information, get the product into individual contributors' hands, then approach the decision-maker with internal adoption metrics. [alex-vacca/outbound-triggers-6]

### Community mentions
- Seven mention classes, each with its move and responder: praise (like/reply, founder voice) / customer question (support handle) / public complaint (acknowledge, take to DM, never argue) / comparison shopping (AE via DM, honest about where you win and lose) / competitor-switch signal (warm DM, fast) / unbranded pain (founder comment, perspective not pitch) / noise. [ido-goldberg/community-radar]
- Default to DM for anything sales-adjacent; go public only for praise, helpful Q&A and pain-mention perspective, and only with replies that survive any future reader; never name a competitor pejoratively even if the poster did. [ido-goldberg/community-radar]
- Route by stakes: low (praise, generic question) may auto-reply; medium (comparison, switch) goes to the AE as a task with a human-drafted DM; high (complaint, crisis) triggers an immediate notification. Reply within 24-48h; after a week a reply looks bot-driven. [ido-goldberg/community-radar]
- After 10-20 fires, prune to brand + competitor + the 3-5 highest-signal pain phrases; switch and comparison signals usually out-convert pain mentions; Reddit often beats X for B2B signal. [ido-goldberg/community-radar]

### Events
- Event class sets the angle: owned event (the topic they came for), exhibited (booth interaction), attended only (shared experience, "what stuck with you"), competitor's event (soft displacement, no aggression), partner event (joint buyer). Follow up within 48-72h; after that the freshness is gone. [ido-goldberg/event-radar]
- Never pretend a booth conversation happened; anonymous company-level attendance never fires individual outreach (tag the account, watch for return signals); the session watched or booth question logged IS the message, "thanks for coming" is not. [ido-goldberg/event-radar]
- CRM cross-check per attendee: active sequence -> flag the rep, do not re-fire; customer -> CSM advocacy signal; open deal -> owner, acceleration signal; net-new -> cold play anchored on the event; cap at 2-3 touches; tag conversions by event name to learn which event classes yield. [ido-goldberg/event-radar]

### LinkedIn event attendee monitor
- Route by funnel stage before any ICP check: attendee whose employer is a Customer or open Opportunity -> FYI to the account owner only (name, title, employer, post URL), never prospecting copy; company-page posts tag the account as attending; only non-customer employers go through the full ICP check, with no lowered bar for local events. [brianne-thomas/linkedin-event-attendee-monitor]
- Harvest mechanics: several event phrases and hashtags in one post-search run (week window, sorted by date, ~40 posts/query), run every 3 days so windows overlap, dedupe by post URL in a dated processed-posts note the scheduled run can write to, prune entries older than 14 days. [brianne-thomas/linkedin-event-attendee-monitor]
- Output stays draft-only: a short comment stating only the shared attendance (no fake reaction to the post) and a connection note with a coffee ask (sends only if the sender has Sales Navigator); the agent never likes, comments or connects, and no sequence is built until a sender is assigned. [brianne-thomas/linkedin-event-attendee-monitor]
