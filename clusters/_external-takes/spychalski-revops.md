- ✅ supports [revops/knowledge/data-governance.md — CRM data quality]: names the four CRM-rot failure modes — stale, incorrect (incl. provider-supplied wrong data from ZoomInfo/Apollo), empty, and unstructured/non-uniform — and stresses that a one-time cleanup goes stale within a year, so the fix must be a continuously-running system, not a project.
- 🆕 new-angle: **enrich-then-validate ordering is data-point-dependent.** Validate-FIRST for email/phone (cheap to check before you re-find). Enrich-FIRST-then-validate for things with no direct checker (e.g. fundraising round: you can't "validate" a round field, you must find the new round and diff it against the stored value). Run basic normalization formulas BEFORE any cross-check, or false flags fire ("fintech" vs "financial technology" read as different → needless re-writes).
- 🆕 new-angle: **CRM enrichment is a fragile exercise — start on a list you don't care about.** Mature CRMs carry hierarchy/dedup/parent-child rules and workflow errors; never "throw all CRM data in, update, push." Prove the pipeline on a throwaway list view first, review every run before push, then let it run continuously on net-new records via a Clay list-view import (self-improving; only revisit when the enrichment logic itself changes).
- ⚠️ contradicts [reference/claude-code-gtm-architecture.md — "run GTM entirely inside one terminal" / Claude Code as the do-everything layer]: for CRM writes specifically, **use Clay, not an agent.** Clay's Salesforce push is DETERMINISTIC (field-mapped, not agentic), lets you inspect every run pre-push, and is the compliant/safe path; "you shouldn't have an agent running willy-nilly in your CRM right now." Both sides. gtm-master (Claude Code architecture): agentic GTM incl. CRM inside the terminal. Spychalski: Claude Code for most workflows, but Clay for CRM enrichment/push until agents are safe enough (maybe ClaudeForce later).
